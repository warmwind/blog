原文标题：Supercomputer networking to accelerate large scale AI training<br>
原文链接：https://openai.com/index/mrc-supercomputer-networking/

前沿模型的训练依赖于可靠的超级计算机网络，这些网络需要在 GPU 之间快速传输数据。为了使这一过程更快速、更高效，OpenAI 与 AMD、Broadcom、Intel、Microsoft 和 NVIDIA 联合开发了 MRC（多路径可靠连接，Multipath Reliable Connection）：一种能够提升大型训练集群中 GPU 网络性能和弹性的新型协议。我们今天通过开放计算项目（Open Compute Project，OCP）发布了 MRC，以便整个行业能够使用它。

每周有超过 9 亿人使用 ChatGPT，我们的系统正成为 AI 的核心基础设施，帮助全球的个人和企业使用日益强大的模型进行构建。在 Stargate 项目启动之前，我们与合作伙伴密切协作，历时数年，共同开发、搭建并维护了我们的前三代超级计算机。这段宝贵的经历使我们坚信：要在 Stargate 规模的算力下高效运作并实现我们的使命，就必须重新思考并大幅降低技术栈每一层的复杂性——包括网络设计。

发布 MRC 规范是 OpenAI 整体计算战略的组成部分：在关键基础设施层建立共享标准，有助于在更广泛的合作伙伴生态中更高效、更可靠地扩展 AI 系统。在本文中，我们将介绍 MRC 的设计，包括：i）它如何支持构建多平面高速网络，在使用更少组件和更低功耗的同时实现冗余，以抵御网络故障；ii）MRC 的自适应数据包分散投递如何从根本上消除核心网络拥塞；以及 iii）我们的部署如何使用静态源路由绕过故障并消除整类动态路由故障。这些优势协同配合，让我们能够更快地向所有人交付更好的模型。

## 为什么网络需要全新设计

在训练大型 AI 模型时，单个步骤可能涉及数百万次数据传输。任何一次传输的延迟都可能波及整个训练任务，可能导致 GPU 闲置。网络拥塞、链路和设备故障是传输延迟与抖动最常见的根源。

随着集群规模的增大，这些问题会变得更频繁，也更难解决。这使网络技术成为 Stargate 设计中的关键环节。

为了支撑当前规模的 Stargate 超级计算机，我们面临两项核心网络挑战。首先，在条件允许的情况下，我们应尽量降低网络拥塞发生的可能性。当然，某些瓶颈是不可避免的，比如两个 GPU 同时向同一目的地发送数据。但在这类情况之外，我们应通过设计来避免拥塞。

其次，我们需要将网络故障对训练任务本身的影响降至最低。在足够大的规模下，即使是最优质的网络，也会持续出现一定程度的链路和交换机故障。过去，单次故障往往会导致训练任务崩溃，被迫从上一个保存的检查点重新开始，或在网络重新计算路由时停滞数秒。这样的中断既浪费 GPU 周期，也耗费时间。对于同步预训练而言——即多台计算机上的大量 GPU 协同步调，共同训练一个 AI 模型——这一问题尤为突出。训练任务规模越大，单次链路波动或故障的影响就越大。这类工作负载本质上是一种"故障放大器"，因此防止此类情况的发生已成为重中之重。

## 我们的解答：MRC

我们的目标不只是构建一个快速的网络，更要构建一个即使在出现故障时也能提供高度可预测性能的网络，确保训练任务持续推进。

为了实现这种可靠性，我们的 Scaling 团队在过去两年里与 AMD、Broadcom、Intel、Microsoft 和 NVIDIA 合作，共同开发了一种全新的网络构建与运营方式。这项工作的成果是我们称之为多路径可靠连接（Multipath Reliable Connection，MRC）的技术。这是一种内置于最新 800Gb/s 网络接口的新型网络协议，使我们能够将单次传输分散到数百条路径上、在微秒级时间内绕过故障，并运行更简洁的网络控制平面。

MRC 对 RoCE（融合以太网上的远程直接内存访问，RDMA over Converged Ethernet）进行了扩展——RoCE 是 InfiniBand 贸易协会（IBTA）制定的标准，支持 GPU 和 CPU 之间基于硬件加速的远程直接内存访问。MRC 借鉴了超级以太网联盟（Ultra Ethernet Consortium，UEC）开发的技术，并通过基于 SRv6 的源路由对其进行扩展，以支持大规模 AI 网络架构。

MRC 已部署于 OpenAI 用于训练前沿模型的所有最大规模 NVIDIA GB200 超级计算机上，包括我们位于德克萨斯州阿比林市、与 Oracle 云基础设施（OCI）合作的站点，以及 Microsoft 的 Fairwater 超级计算机。MRC 已用于训练多个 OpenAI 模型，利用了来自 NVIDIA 和 Broadcom 的硬件。今天，MRC 规范作为开放计算项目（OCP）的贡献公开发布，供社区使用和进一步构建。我们还共同撰写了一篇论文，详细记录了我们的实践经验——"Resilient AI Supercomputer Networking using MRC and SRv6"（使用 MRC 和 SRv6 构建弹性 AI 超级计算机网络）。

## 基础：多平面网络

构建高度弹性的网络，首先需要从具备足够天然冗余的网络拓扑出发，确保即使网络中的链路或交换机发生故障，所有数据流也能获得良好性能。

我们不再将每个网络接口视为一条 800Gb/s 的链路，而是将其拆分为多条较小的链路。例如，一个接口可以连接到八台不同的交换机。这样就可以构建八个独立的并行网络（即平面），每个平面以 100Gb/s 运行，而不是构建单一的 800Gb/s 网络。

这一变化对集群的形态产生了深远影响。一台能连接 64 个 800Gb/s 端口的交换机，换为 100Gb/s 后可以连接 512 个端口。这使得仅用两层交换机就能构建完整连接约 131,000 个 GPU 的网络。而传统的 800Gb/s 网络则需要三到四层交换机。

![MRC 多平面网络拓扑：仅用两层交换机即可连接超过十万个 GPU](https://images.ctfassets.net/kftzwdyauwt9/hMXzAlcJ2ZoyVk4XhCqZc/f0f074764da3f50d60f8a9e030bf0c29/Diagram_1_-_desktop_-_light.svg)

*MRC 对多平面网络的支持意味着我们只需两层交换机即可连接超过十万个 GPU。与传统方案相比，这降低了所需功耗、减少了可能发生故障的组件数量，并降低了网络的总体成本。*

这样构建出的网络成本更低、功耗更少，并提供比传统网络设计更丰富的路径多样性。它还允许更多流量在 Tier 0 交换机本地转发，从而提升性能。

然而，充分利用如此丰富的路径多样性并非易事。用于 AI 训练的传统网络协议通常要求每次传输遵循单一路径，以确保数据包按序到达。在大型多平面网络中，这会带来两个问题：不同的数据流可能在同一条链路上发生碰撞并造成拥塞，而且每条数据流只能使用一个可用平面。如果不做任何改变，多平面网络反而会导致严重拥塞和整体性能下降。

![单路径数据流导致的链路拥塞示意图](https://images.ctfassets.net/kftzwdyauwt9/2Amv4FWRbv6EAI4PqTtUd6/ea33aef009c0b317bf8cd9eeebb3622a/Diagram_2_-_desktop_-_light.svg)

*在单路径数据流的经典 RoCE 部署中，各条链路频繁出现拥塞。由于集合通信对最坏情况下的延迟极为敏感，这对 AI 训练工作负载的影响尤为严重。*

*数据包流在传输过程中发生碰撞导致拥塞（动画：由 Mark Handley 制作）。*

## MRC 的转变：将数据包分散投递至数百条路径

MRC 从根本上改变了这一模型。MRC 不再将一次传输分配给单一路径，而是将单次传输的数据包分散投递到网络中数百条路径上，横跨所有不同的平面。数据包可能乱序到达，但所有 MRC 数据包均包含其最终内存地址，目的端可在数据包到达时将其直接送入内存。

![MRC 数据包分散投递：同时将数据包分散到多条路径上](https://images.ctfassets.net/kftzwdyauwt9/6o8SiUEq5zJnWw7qDwJ5ur/e92de63c6f6fa65555275b6ef48997b9/Diagram_3_-_desktop_-_light.svg)

*MRC 同时将数据包分散到多条路径上，从而减少可能拖慢同步 AI 训练的拥塞。*

通过将流量分散到多条路径，MRC 避免了网络中的热点，防止某些传输所需时间远超其他传输。这避免了会影响同步 AI 训练的速度下降。

*数据包分散投递到多条路径（动画：由 Mark Handley 制作）。*

每个 MRC 连接会为其使用的众多路径维护少量状态信息。如果检测到某条路径开始出现拥塞，它会将该路径替换为另一条，从而均衡网络负载。如果丢失数据包，它会采取最保守的做法：假设该路径上某处可能已发生故障，立即停止使用该路径，并重传可能丢失的数据包。MRC 弃用某条路径后，会发送探测数据包检查是否真的发生了故障，以及故障是否已恢复。

数据包丢失的原因并非只有故障，目的端拥塞也是常见诱因之一。MRC 通过数据包裁剪来处理这种情况。如果交换机因拥塞而需要丢弃数据包，它会裁剪掉负载，仅将报头转发给目的端，触发显式重传请求。数据包裁剪减少了误判——即错误地将丢包视为路径故障的情况。

多平面拓扑、分散投递、负载均衡和数据包裁剪的组合，使 MRC 连接能够在微秒级时间内检测网络故障并绕过它，将对同步训练任务的影响降至最低。相比之下，传统网络架构可能需要数秒乃至数十秒才能稳定并完成故障绕行。

## 以源路由替代动态路由

MRC 使我们能够在简化网络方面更进一步。

传统上，交换机运行 BGP（边界网关协议，Border Gateway Protocol）等动态路由协议来计算可用路径并绕过故障。但交换机是运行复杂软件的复杂设备。当它们以微妙的方式出错时，这些问题往往难以诊断，并可能导致连接失败，直到问题被修复。

有了 MRC，动态路由变得不再必要。如果某条路径上出现数据包丢失，MRC 会停止使用该路径。我们采取了更为激进的方案：禁用动态路由，改为使用 IPv6 段路由（即 SRv6）。SRv6 让发送方能够直接为每个数据包指定其在网络中应经由的路径，方法是将交换机标识符序列嵌入每个数据包的目的地址中。

![SRv6 源路由图：发送方对每个数据包的完整路径进行编码](https://images.ctfassets.net/kftzwdyauwt9/1f8McRrpdgN3uVXEYpGDiM/561c3b78269c13e27b7812c5ccf34922/Diagram_4_-_desktop_-_light.svg)

*SRv6 允许发送方对每个数据包应经由网络的完整路径进行编码。由于路径是确定性的，发送方可以独立响应给定路径上的拥塞或丢包情况。*

具体来说：在转发时，交换机检查自身的标识符是否存在。若存在，则通过移位目的地址将该标识符删除，从而露出下一台交换机的标识符。交换机随后在静态路由表中查找该标识符，以确定下一跳的发送目标。与动态路由不同，这张静态路由表在交换机首次配置时写入，此后不再更改。

MRC 使用 SRv6 将数据包同时分散投递到所有网络平面，以及每个平面上的多条路径。如果某条路径失效，MRC 只需停止使用该路径。交换机无需重新计算路由，只需按照预配置的静态路由盲目转发即可。

## 生产环境中的实际表现

我们的训练网络拥有数百万条链路。虽然这些网络质量很高，但在足够大的规模下，一定程度的链路波动是不可避免的。在训练过程中，我们曾观察到 tier-0 与 tier-1 交换机之间每分钟出现多次链路波动，但 MRC 确保了这些波动对我们的同步预训练任务没有任何可测量的影响。实际上，其影响之小，使我们甚至不需要优先安排对这些链路的立即修复。

不只是链路会发生故障。在为 ChatGPT 和 Codex 训练最近一个前沿模型期间，我们不得不重启四台 tier-1 交换机。过去，重启交换机需要运维团队极为谨慎地操作，以避免干扰训练。使用 MRC 之后，我们甚至无需与集群中正在运行训练任务的团队进行协调。链路修复同样如此。以往进行维护工作时，我们需要与运维团队协调以停用链路。现在，我们可以在链路仍处于服务状态时进行修复。如果链路工作状态良好，MRC 就会使用它；否则，MRC 会在它修复之前将其绕过。

![训练过程中采集的真实数据，展示了 MRC 对 T1 交换机完全宕机的响应](https://images.ctfassets.net/kftzwdyauwt9/rXJCOvyQlsY8yFyXdl9Li/6353f2f9a9d41bbbac7d965f49d42db3/Diagram_5_-_desktop_-_light.svg)

*训练过程中采集的真实数据，展示了 MRC 对 T1 交换机完全宕机的响应。训练任务出现了短暂的速度下降，但很快恢复正常。*

在 MRC 之前，如果 GPU 的网络接口与 tier-0 交换机之间的链路发生故障，训练任务就会失败。有了 MRC，任务能够以合理的性能继续运行。如果一块 8 端口的网络接口损失了一个端口，最大传输速率就会降低八分之一。MRC 会检测到这一情况，重新计算路径以绕过故障平面，并立即通知对端不要在入站流量中使用该平面。大多数故障链路在一分钟内就能恢复，此时 MRC 会重新将该平面投入使用。

GPU 接口链路丢失引发的速度下降在不同训练任务中有所差异，但实际上往往显著低于物理容量损失的比例。

## 关键改进

MRC 最终为我们扩展超级计算机规模带来了三项关键优势。

首先，它使我们能够仅用两层以太网交换机，为超过 100,000 个 GPU 的超级计算机构建多平面高速网络。与等效的三层或四层单平面网络相比，这既提供了足够的冗余来抵御网络故障，又降低了功耗。

其次，MRC 的自适应数据包分散投递实现了充分的负载均衡，使我们在网络核心中几乎观察不到任何拥塞。这大幅降低了同步训练期间各数据流之间的吞吐量差异——而消除异常值正是性能的核心所在。这也意味着当多个任务共享集群时，它们不会相互影响对方的性能。

最后，MRC 使用 SRv6 源路由快速绕过故障，仅通过正常工作的路径发送数据包。这使我们能够运行简单的静态网络控制平面，并消除整类动态路由故障行为。

## 开放协议

MRC 显著提升了我们训练新前沿模型的能力，确保我们的网络能够跟上研究人员雄心勃勃的 AI 路线图。它相较于此前的方案实现了实质性改进，有助于加速我们的目标——可靠地将 AGI 的益处带给每一个人。我们为促成这一成果的跨行业合作感到自豪。

随着训练集群持续扩大，网络设计越来越决定着可用算力能够真正得到利用的程度。MRC 帮助我们在拥塞、链路故障以及曾经会打断训练的维护事件中保持 GPU 协同工作。在有意义的规模下，这种可靠性和效率不是锦上添花，而是使同步前沿模型训练成为可能的关键所在。

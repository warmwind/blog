原文标题：The Agent Development Lifecycle<br>
原文链接：https://www.langchain.com/blog/the-agent-development-lifecycle

![Agent Development Lifecycle](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff680685c3d0b696ee5823_pic1.png)

每个人都想交付 Agent。

最优秀的团队已经找到了反复、安全、系统地做到这一点的方法。他们早早上线，从真实使用中学习，快速迭代。他们不把 Agent 视为一次性的 Demo 或孤立的项目。

相反，他们构建了一套 **Agent 开发生命周期**，通过将实验转化为可重复的交付、学习和持续改进体系来形成持续的推进动力。

这个生命周期由四个部分组成：

**构建 → 测试 → 部署 → 监控**

![Agent 开发生命周期四阶段示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78da_99648614.png)

这个顺序是有意为之的。测试应该在 Agent 进入生产环境之前就开始，而不是在之后。团队需要在部署前测试 Agent，以受控的方式部署，监控它在生产中的表现，并将这些经验反馈到下一个构建和 eval 循环中。

对于单个 Agent，这个流程可以保持轻量级。跨多个 Agent 时，它就成了一个基础设施和治理挑战。团队需要共享的方式来控制成本、管理工具访问权限、检查工具调用、复用上下文，并决定哪些环节需要人工介入。

从让 Agent 工作一次，到将构建 Agent 转化为可重复实践，差别就在于是否建立了正确的开发生命周期。

## 构建

构建阶段是团队决定创建什么类型的 Agent 系统以及使用什么抽象层级的阶段。

这里有各种各样的工具选择，有的以代码为核心，有的则是无代码或低代码。有些专注于抽象，有些则专注于为 Agent 提供一个配备了提示词、工具、技能和状态的工作环境。

![构建阶段工具生态示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78e0_14009bc9.png)

在代码优先的方向上，团队通常会选择开源框架和 harness。在 LangChain 生态系统中，这包括 [LangChain](https://www.langchain.com/langchain)、[LangGraph](https://www.langchain.com/langgraph) 和 [Deep Agents](https://www.langchain.com/deep-agents)。LangChain 生态系统之外的例子包括 CrewAI 和 Claude Agents SDK。

这些工具在技术栈的不同层次上运作。

**Agent 框架**主要专注于抽象。它们帮助开发者组合模型调用、工具、提示词、检索、结构化输出和 Agent 循环。LangChain 和 CrewAI 是这一类别中的典型例子。

**Agent 运行时**专注于执行。它们支持需要状态、控制流、持久性和人工介入的 Agent。LangGraph 是 LangChain 生态系统中最典型的例子。它提供了一种构建能够分支、循环、暂停、恢复并在多次交互或任务中保持持久化状态的 Agent 系统的方法。

**Agent harness** 专注于执行实体工作。它们为 Agent 长时间运行任务所需的周边结构提供支持：提示词、技能、MCP 服务器、钩子、中间件，有时还包括文件系统。Deep Agents 和 Claude Agent SDK 是这种模式的典型例子。

这些区别很重要，因为"构建一个 Agent"可以意味着不同的事情。

对于简单的应用，可能只需要定义一个工具调用循环。对于更复杂的 Agent，可能涉及编写提示词、定义技能、连接 MCP 服务器、配置中间件，以及设置 Agent 可以随时间检索或更新的上下文。

*无代码构建*

构建阶段还有无代码和低代码这一方向。LangSmith Fleet、Claude Cowork 和 n8n 等工具让更多人能够参与 Agent 开发。这一点很重要，因为了解所需工作流程的人并不总是会写代码的人。

![无代码构建工具示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78dd_5f6458d6.png)

与此同时，无代码工具并不能消除对工程控制的需求。随着系统变得更加复杂，团队通常需要能够在代码层面扩展或覆盖行为的方式。钩子和中间件在这里尤为重要，因为它们允许团队在不从头重建每个 Agent 的情况下，围绕工具调用、上下文处理、审批、认证或业务规则添加自定义逻辑。

最好的构建环境让简单的事情简单，复杂的事情成为可能。它们允许领域专家编辑提示词、技能和上下文，同时仍然让工程师控制那些需要可靠、可测试和受治理的部分。

## 测试

在 Agent 部署之前，团队需要一种方法来确定它是否真正准备好了。

这并不意味着在任何人使用 Agent 之前就构建一套完美的 eval 套件——在实践中，这很少是现实的。但这确实意味着需要有足够的 eval 来捕获明显的失败、比较不同版本，并避免盲目发布变更。

![测试阶段示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78d4_4627dcc1.png)

大多数 eval 工作流从一个小型代表性任务数据集开始。一些示例来自预期使用案例，另一些来自手动测试、内部试用、支持工单、历史追踪记录或已知的边缘情况。随着时间的推移，生产追踪记录会使这些数据集更加强大，但测试应该在进入生产之前就开始。

*数据集和指标*

数据集是团队保留所学内容的方式。没有它们，同样的失败在提示词变更、模型升级或工具更新之后往往会重复出现。

正确的指标取决于任务。

在某些情况下，存在明确的正确答案。Agent 是否提取了正确的值？是否选择了正确的标签？是否更新了正确的字段？这些任务可以直接衡量正确性。

其他时候，不存在单一的正确答案。Agent 可能需要撰写回复、总结对话、决定是否升级，或者以多种有效路径完成任务。在这些情况下，团队更多地依赖基于标准的评估。问题变成了：回复是否有依据？Agent 是否遵守了政策？是否要求了澄清？是否在没有不必要工具调用的情况下高效完成了任务？

*实验*

实验是将数据集和指标与迭代联系起来的桥梁。它们允许团队针对同一评估集比较提示词、模型、检索策略、工具 schema 和编排模式。随着时间的推移，这些实验会展示 Agent 是在改进还是在退步。

目标不是在第一天就创建一套完美的 eval 套件，而是从一套有用的套件开始并持续改进它。最有价值的 eval 数据集来自最困难的示例：首先来自开发和内部试用，然后来自生产环境。

*模拟*

模拟是测试的另一个重要组成部分。

许多 Agent 是多轮系统。它们不只是回答一个问题，而是进行对话、收集信息、调用工具、更新状态，并从模糊性中恢复。对于这些 Agent 来说，单轮 eval 是不够的。团队需要多轮 eval 和模拟的端到端交互。

语音 Agent 是一个明显的例子，但这个模式更广泛。任何在多轮交互中运行的 Agent 都可能需要模拟。一个支持 Agent 可能需要处理沮丧的客户、提出后续问题、检查订单状态，并决定是否需要升级。一个编程 Agent 可能需要检查代码库、进行更改、运行测试，并响应反馈。一个内部运营 Agent 可能需要在采取行动之前收集缺失的信息。

良好的测试实践帮助团队系统地改进 Agent，而不是依靠感觉。它们将预期行为转化为数据集，将数据集转化为实验，将实验转化为更好的系统版本。部署后，监控会提供使这些 eval 更强大的真实世界示例。

## 部署

一旦 Agent 经过构建和评估，它就需要一个能够可靠运行的环境。

对于简单的 Agent，部署可能与部署传统应用程序相似。但许多 Agent 需要的不仅仅是一个无状态服务器。它们运行时间更长，调用工具，等待人工输入，写入文件，从中断中恢复，并在多次交互或任务之间维护状态。

![部署阶段示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78d1_beca6459.png)

这就是为什么运行时很重要。

生产 Agent 运行时通常需要支持持久化执行和人机协作模式。持久化执行意味着 Agent 可以在某处设置检查点并在出现问题时恢复，而不是丢失工作成果。人机协作意味着 Agent 在需要批准、澄清或审查时可以暂停。

目前有现成的解决方案。[LangSmith Deployment](https://docs.langchain.com/langgraph-platform) 提供了部署和管理 Deep Agents 及 LangGraph Agent 的基础设施。AWS AgentCore 是托管 Agent 运行时的另一个例子。一些团队也在 Temporal 等系统之上构建自己的运行时，尤其是当他们在技术栈的其他地方已经使用 Temporal 来处理长时间运行的工作流时。

*沙箱*

许多 Agent 还需要专用的执行环境。

Agent 越来越需要编写代码、执行代码、检查文件、转换文档或与文件系统交互。在这些情况下，团队需要决定这些工作在哪里进行。沙箱是一种常见的解决方案，它们提供了隔离的执行环境和文件系统访问，同时减少了错误或不安全行为的"爆炸半径"。

例子包括 [LangSmith Sandboxes](https://www.langchain.com/blog/introducing-langsmith-sandboxes-secure-code-execution-for-agents/)、Daytona 和 E2B。

并非每个 Agent 都需要完整的沙箱。在某些情况下，Agent 只需要一个存储和检索文件的地方。虚拟文件系统可能就足够了。Deep Agents 支持这种模式，允许 Agent 将文件用作工作记忆，而不必在沙箱内执行任意代码。在底层，该文件系统可能由 Postgres 或 S3 等系统支持。

*Context Hub*

部署中另一个常被忽视的部分是提示词和上下文管理。

Agent 中一些最重要的部分不是传统的应用代码。提示词、检索上下文、技能和任务指令的变更频率可能高于应用程序本身，而且它们可能需要由非工程师人员来编辑。

这就产生了对提示词或 Context Hub 的需求：一个存储、版本化、审查和更新 Agent 非代码部分的地方。这允许团队在无需完整部署的情况下调整 Agent 行为，并让领域专家掌控他们最了解的上下文。

在实践中，部署不仅仅是将 Agent 放到服务器上，而是为 Agent 提供它完成真实工作所需的运行时、执行环境和上下文管理系统。

## 监控

一旦 Agent 部署完毕，团队就需要了解它们在生产中的实际表现。

这是监控 Agent 与监控传统软件不同的地方。延迟、成本、错误率和运行时间等指标仍然重要，但它们只是整体情况的一部分。Agent 可以返回技术上成功的响应，但仍然未能完成任务本身——它可能调用了错误的工具，依赖了错误的上下文，跳过了必要的审批步骤，或者产生了听起来合理但实际上是错误的答案。

![监控阶段示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78d7_8e9617a3.png)

要理解这些失败，团队需要追踪记录（traces）。

追踪记录捕获了 Agent 的完整轨迹：它接收的输入、发出的模型调用、调用的工具、收到的输出，以及最终的响应或操作。这是理解 Agent 实际做了什么所需的细节层级。

这就是为什么我们认为 [Agent 可观测性驱动 Agent 评估](https://www.langchain.com/blog/agent-observability-powers-agent-evaluation)，以及为什么 [Agent 改进循环从追踪记录开始](https://www.langchain.com/blog/traces-start-agent-improvement-loop)。如果你看不到轨迹，就无法可靠地调试行为，也无法将那些失败转化为未来的 eval。

*信号*

监控还应包括从这些追踪记录中提取信号。

其中一些信号可以来自 LLM-as-judge 评估器。例如，一个 judge 可以评分 Agent 是否回答了用户的问题、是否遵守了政策、是否使用了正确的语气，或者是否完成了任务。其他信号可以更简单——正则表达式可以检查是否出现了必要的短语、是否调用了被禁止的工具，或者是否出现了已知的失败模式。

这些信号不仅对质量检查有用，还可以成为一种产品分析工具。它们可以告诉你用户要求 Agent 执行哪些任务、Agent 在哪里卡住、用户纠正 Agent 的频率，以及用户在哪里感知到了错误。

*反馈*

反馈是监控的另一个核心部分。

仅仅存储追踪记录是不够的。团队还需要将反馈与这些追踪记录一起存储。这些反馈可以来自 LLM judge、基于正则表达式的信号、人工审查者，或者通过 API 收集的直接用户反馈。例如在 LangSmith 中，团队可以将用户反馈直接附加到底层运行记录上，这使得将"用户不满意"与"Agent 在三步前调用了错误的工具"联系起来变得更容易。

*仪表板*

最后，团队需要能够展示趋势随时间变化的仪表板和告警。

一个有用的 Agent 仪表板应跟踪使用量、反馈、延迟、成本、工具调用、评估器得分和反复出现的失败模式等指标。告警应在重要阈值被突破时触发，例如延迟上升、成本增加、工具失败、用户反馈下降或政策违规激增。

良好的监控不仅仅是了解系统是否在运行，而是了解 Agent 是否在做正确的工作、以正确的方式运作，并随时间不断改进。

最强大的监控系统能直接反馈到评估中。重要的追踪记录成为数据集示例，反复出现的失败成为指标，而生产行为则成为下一轮改进的基础。

## 迭代

最优秀的团队快速而系统地穿越 Agent 开发生命周期。

他们不会等到 Agent 完美才上线，而是构建有用的东西，充分测试以理解其行为，以受控方式部署，监控其在生产中的表现，并将这些经验反馈到下一个版本。

这并不意味着草率发布，关键是要有可见性。

拥有数据集、实验、追踪记录、反馈和仪表板的团队可以直接从真实使用中学习。他们可以在广泛推出变更之前先进行测试，识别生产中出现的问题，将失败转化为 eval，并在不依赖猜测的情况下改进 Agent。

这就是团队如何爬山（hill-climb），以及 Agent 系统如何随时间改进。

最有效的团队会找到困难的示例，理解 Agent 为何失败，并调整提示词、工具配置、检索策略、模型、中间件或工作流。他们重新运行 eval，部署更好的版本，监控又给了他们下一批边缘案例和失败。

在企业内部，挑战在于让这个循环在团队间可重复。

如果每个团队都必须从头构建自己的 eval 框架、部署基础设施、追踪系统、反馈流水线和仪表板，Agent 开发就会进展缓慢。最有效的组织投资于共享基础设施，这样团队可以在不不断重新发明底层系统的情况下推进生命周期。

这就是 Agent 开发生命周期成为一项运营实践的原因。

## 治理

治理围绕整个 Agent 开发生命周期。

对于单个 Agent，轻量级控制可能就足够了。随着组织部署更多 Agent，治理变得必不可少。没有它，团队很快就会发现 Agent 难以发现、难以监控、运行成本高昂，且不清楚它们被允许做什么。

![治理阶段示意图](https://cdn.prod.website-files.com/65c81e88c254bb0f97633a71/69ff682de4638684801c78ce_1e0b2abf.png)

*成本*

第一个治理挑战是成本。

Agent 可能会变得昂贵，因为它们可能涉及多次模型调用、长 Context Window、重复使用工具、重试，或者运行时间较长。组织需要通过预算、使用监控、告警以及对哪些 Agent、团队、模型或工具在推动成本方面的可见性来追踪和管理这些支出。

*工具访问*

第二个治理挑战是工具访问。

Agent 之所以有用是因为它们可以采取行动，但这也引入了风险。团队需要明确控制哪个 Agent 可以访问哪些工具、在什么条件下，以及代表哪些用户。

这就是审计追踪变得重要的地方。如果一个 Agent 调用了某个工具，组织应该能够检查是哪个 Agent 发出了调用、使用了什么输入、产生了什么输出，以及是哪个用户或政策授权了该操作。工具调用往往是 Agent 行为对业务产生影响的地方，因此它们需要是可观测且可审查的。

人机协作是另一个重要的治理机制。

并非每次工具调用都应该完全自动化。有些操作应该暂停以供人工审查，尤其是涉及客户、金融系统、敏感数据或生产基础设施的操作。人机协作的工作流在从一开始就被设计进系统时效果最好。

*可发现性*

第三个治理挑战是可发现性和复用。

随着组织构建更多 Agent，他们也积累了更多可复用的资产——提示词、技能、工具、检索来源、政策，甚至其他 Agent。如果没有良好的发现和治理机制，团队往往会反复重新创建这些组件，导致不一致。共享的上下文和共享的 Agent 需要是可发现、可复用且受治理的。

这对技能来说尤其重要。技能可以编码工作流程、写作风格、特定领域的程序，或者使用工具的说明。如果一个团队已经构建了好的技能，另一个团队应该能够找到它，而不是从头写一个新版本。

良好的治理不是为了让团队慢下来，而是在 Agent 系统扩展时，在不失去可见性、控制和一致性的前提下，让快速迭代成为可能。

## 结论

最优秀的组织已经开始以这种方式运作。他们早早上线，但不会盲目上线。他们在部署前进行评估，在部署后监控行为，并持续利用所学内容让下一个版本更好。

这就是 Agent 开发变得可重复的原因，也是让 Agent 从 Demo 进入可靠生产系统的关键。
